Wanderly MVP — Master Prompt for a Coding Agent

You are a senior iOS engineer, product designer, game-systems designer, and QA engineer. Build a production-quality MVP of Wanderly, a location-based running and exploration game.

Wanderly turns the real world into a game map. The map begins covered by fog. As the user physically walks, runs, or hikes, fog is permanently cleared around the traveled path. Users discover checkpoints, open reward chests, earn XP and coins, collect badges/fragments, complete missions, and review every individual activity.

Use other real-world exploration apps only as category references. Do not copy their UI, assets, names, wording, icons, map style, or proprietary mechanics. Wanderly must have an original identity.

1. Working rules

Inspect the entire existing repository before changing code: architecture, models, services, views, assets, dependencies, deployment target, backend, tests, signing, and CodeMagic configuration.

Preserve useful existing Wanderly code. Do not replace a working project with a new template.

Read and follow repository instructions such as AGENTS.md.

Check git status; preserve unrelated user changes.

Produce a short implementation plan, then implement it fully.

Do not stop at static mockups. Primary navigation, state, persistence, map behavior, tracking, rewards, and history must work.

Do not leave dead buttons, fake login, fake purchase success, or permanent placeholder data in release code.

Never hardcode production secrets or StoreKit prices.

Use protocols for authentication, purchases, location, persistence, checkpoint, and sync services.

Ask only when credentials or an irreversible external decision truly blocks the task.

2. Platform and architecture

Build iOS first using the existing native Swift project.

UI: SwiftUI.

Advanced map overlays: MapKit MKMapView wrapped for SwiftUI.

Location: Core Location.

Purchases: StoreKit 2.

Haptics: Core Haptics or UIKit feedback generators.

Persistence: preserve the existing layer; otherwise use SwiftData when supported or Core Data for an older target.

Backend: preserve the existing backend. If none exists, create clean service/repository interfaces and a Supabase-ready implementation for authentication, user profiles, checkpoints, claims, rewards, and cloud backup. Keep a local development implementation so the UI and tests can run without production credentials.

Architecture: lightweight MVVM, feature-based folders, dependency injection, Swift Concurrency.

Deployment target: preserve the current target unless a documented technical reason requires a change.

Cloud builds: preserve or add a CodeMagic-compatible build workflow. The owner works on Linux and uses CodeMagic, not a local Mac workflow.

Suggested modules: App, Core/DesignSystem, Core/Location, Core/Map, Core/Persistence, Core/Purchases, Core/Auth, Features/Onboarding, Features/Paywall, Features/Auth, Features/Map, Features/ActiveRun, Features/Journey, Features/Checkpoints, Features/Missions, Features/Collection, Features/Profile, Resources, Tests.

Adapt this organization to the repository; do not force a destructive restructure.

3. Non-negotiable first-launch flow

The exact order is:

Welcome → 10 onboarding questions → Personalized explorer summary → Premium paywall → Login/account creation → Location setup → Main app

Login must not appear before onboarding or the first premium presentation.

Implement an explicit root state machine:

needsOnboarding

needsPaywallPresentation

needsAuthentication

needsLocationSetup

readyForMainApp

Persist every completed gate. On relaunch:

Incomplete onboarding resumes at the last unanswered question.

Completed onboarding but unseen paywall opens the paywall.

Completed/dismissed/purchased paywall but unauthenticated user opens authentication.

Authenticated user without location setup opens location setup.

Otherwise open the main app.

Onboarding happens before authentication, so save answers locally first. After login, migrate them to the authenticated profile without loss or duplication.

If a purchase occurs before login, StoreKit remains the source of truth. Read current entitlements after authentication and synchronize the entitlement with the user account. Premium access must not disappear during login.

9. Contextual location setup

After authentication, explain before requesting permission:

Location while using the app draws the route and clears fog.

Background location can continue an explicitly started activity when the screen locks.

Background GPS may affect battery.

Tracking begins only when the user starts an activity and ends when they finish/discard it.

Permission sequence:

Request When In Use first.

Request Always only when background tracking is enabled or genuinely needed.

Provide limited foreground tracking when Always is denied.

If denied, explain and offer Open Settings.

Never spam permission dialogs.

Ask for notifications later in context, not during onboarding.

11. Fog-of-world map

The Map is the core experience.

Required behavior:

Center on the user and provide a recenter button.

Show location and heading.

Cover unexplored territory with an atmospheric semi-opaque fog.

Keep previously explored territory permanently visible.

Keep explored progress visible at suitable zoom levels; it must not vanish when zooming out.

During a valid active session, each accepted GPS point clears a configurable 20–30 m radius.

Interpolate valid neighboring points into a smooth cleared corridor.

Never bridge implausible GPS jumps.

Persist permanent exploration separately from run history.

Deleting a run does not automatically restore fog.

Recommended implementation:

Use MKMapView for precise overlay control.

Render fog as a large polygon/visible-region overlay with holes using even-odd fill, a mask, or a performant equivalent.

Keep route geometry for journey replay.

Also quantize exploration into stable geographic cells/tiles for deduplication, percentages, rewards, and future sync.

Process only visible geometry and cache simplified geometry by zoom level.

Perform expensive geometry away from the main thread.

Do not rebuild the entire world overlay for every GPS sample.

Improve an existing sound fog renderer instead of replacing it unnecessarily.

12. Active activity session

Before start

Show current position, selected activity (Walk/Run/Hike), nearby checkpoints, weekly progress, and a prominent Start button.

During activity

Show live elapsed time, distance, current/average pace, newly explored amount, nearby checkpoint distance, route line, and fog clearing.

Controls:

Start

Pause

Resume

Finish

Discard with confirmation

Prevent accidental finish/discard. Frequently persist an active-session snapshot so a crash, termination, or signal loss does not erase the activity.

GPS validation must:

Reject invalid/negative accuracy.

Ignore points worse than a configurable 35–50 m horizontal-accuracy threshold.

Avoid distance calculation from one noisy initial fix.

Reject implausible jumps using distance, elapsed time, and activity type.

Use location timestamps.

Add no distance/fog while paused.

Avoid repeated-point double counting.

Flag suspicious segments instead of corrupting the entire route.

Use configurable walking/running/hiking speed thresholds, not scattered constants.

Reduce obvious driving/teleport abuse without deleting a legitimate run because of one noisy GPS point.

Background requirements:

Continue only an explicitly started session when permission allows.

Configure appropriate Core Location background modes.

Never continuously track when no session is active.

Show a clear active-tracking indicator.

Restore UI state on foreground return.

Balance accuracy and battery using distance filters and activity-aware configuration.

14. Checkpoints and rewards

Checkpoint fields: stable ID, coordinate, name, type, activation radius (initially 30–50 m), reward, optional availability window, repeatability, cooldown, active status, and safety status.

MVP types:

Common chest

Rare chest

Landmark

City fragment

When a user enters the radius during a valid session:

Trigger haptic feedback.

Show a small discovery animation.

Allow claim.

Grant XP, coins, or a collectible.

Save idempotently so retries/taps cannot duplicate rewards.

Attach rewards to the current run summary.

Use a backend-controlled production dataset so unsafe points can be removed. Do not place rewards in lakes, highways, private property, restricted areas, or inaccessible locations.

Include a deterministic DEBUG-only Da Nang route and seeded checkpoints to test movement, fog, claims, and summaries. Never expose simulation controls in RELEASE.

Do not build trading, marketplace, crafting, combat, or complex inventory systems.

17. Profile and settings

Profile shows display name, avatar, explorer level/XP, total distance, total sessions, explored cells/area, checkpoints, longest session, weekly target, and Premium status.

Settings include unit, tracking/permission status, fog appearance, haptics, reminders, privacy, data export/deletion entry point, Restore Purchases, Terms, Privacy Policy, Sign Out, and Delete Account.

18. Required data concepts

UserProfile

Store ID, display name/avatar, onboarding answers, all 10 normalized preferences, explorer type, unit, level, XP, coins, weekly target, and entitlement.

RunSession

Store ID, user ID, title, activity type, status, start/end, elapsed/moving seconds, distance meters, average pace, average speed, route points, newly explored cells, checkpoint claims, XP/coins/collectibles earned, cached map preview reference, sync state, and timestamps.

Each route point stores latitude, longitude, timestamp, horizontal accuracy, and optional altitude/speed/course.

ExplorationCell

Store stable cell ID, first/last explored time, optional source run ID, and sync state.

Checkpoint and CheckpointClaim

Store checkpoint definition plus claim user, run, time, verified coordinate/accuracy, reward transaction, and sync state.

Mission/MissionProgress

Support period, target type/value, reward, progress, completion, and claimed state.

RewardTransaction

Use append-only, idempotent transactions so retries cannot duplicate XP, coins, or collectibles.

19. Local-first synchronization

Save active and completed sessions locally first.

Fog clearing works offline.

Queue cloud sync and checkpoint verification when offline.

Never lose a run because a request fails.

Use stable client-generated IDs.

Prevent duplicate sessions, claims, and rewards during retries.

Show subtle pending-sync status without blocking a summary.

20. Design direction

Create an original outdoor-adventure identity:

Deep teal/navy/forest green/fog gray foundations.

Gold/orange reward accents.

Rounded cards, readable typography, subtle elevation.

Map remains dominant.

Small tasteful animations/haptics for fog clearing and rewards.

Avoid clutter and avoid imitating Pokémon GO or MysteryHike.

Support Dynamic Type, VoiceOver, contrast, Reduced Motion, safe areas, common iPhones, loading/empty/error/offline/permission-denied/no-location states.

Keep social sharing private by default.

Hide sensitive share-card endpoints.

Support account/data deletion.

Explain background location and battery use honestly.

Include a reminder to watch traffic and surroundings.

24. Performance

Keep map gestures smooth during tracking.

Throttle UI updates separately from raw persistence.

Do not recompute all explored geometry for every sample.
